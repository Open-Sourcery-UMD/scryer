# Headless import contract v1

`extractBankCsv(bytes, metadata, mapping)` accepts copied `Uint8Array` bytes, `accountRefId`, caller-supplied `observedAt` UTC, and an explicit column mapping. It uses only local Web APIs. The mapping names one ISO `YYYY-MM-DD` date column and either one signed amount column (`positive=credit`, `negative=debit`) or separate credit/debit columns. Exactly one convention is selected; unknown columns, duplicate headers, ambiguous two-sided amounts, invalid UTF-8, malformed CSV, and over-limit inputs return stable typed errors or row warnings without approving history. Filename and MIME detection are advisory only and have no role in value interpretation. The extractor does not infer coverage from transaction dates.

Input limits: 20 MiB raw bytes; 100,000 data records; 256 columns; 64 KiB UTF-8 bytes per decoded field; and 1,000,000 total decoded cells. The composite cell cap is a deliberate lower resource limit: a 20 MiB file can contain millions of tiny comma-separated cells and cause disproportionate array allocation even while meeting each individual cap. A preflight checks CSV quote grammar and counts before the parser allocates rows. A leading UTF-8 BOM and LF or CRLF line endings are supported. Embedded newlines, commas, and escaped quotes in quoted fields are preserved. Bare CR, NUL, unclosed quotes, quote in an unquoted field, and content after a closing quote fail typed. Header names must be nonempty and unique after exact decoding; no case folding or trimming changes identity. Rows must have the header's field count.

The returned `artifact` has `kind:"bank_transactions"`, an account binding, raw-byte SHA-256, and explicit observation time. Its opaque ID is deterministic from the account reference and raw digest. A `proposal` preserves the exact raw amount string, source location `row:N:col:M` (logical CSV record index, counting the header as record 1), parser/mapping versions, and nullable proposed nonnegative cents. The proposal ID is deterministic from artifact identity and row position. Each `candidate` retains the row's raw fields locally, exact source position, parsed ISO date or null, `credit`/`debit`/`unresolved`, and stable warning codes. Zero, invalid, and debit amounts do not become approved bank-credit candidates. A proposal is evidence only; its existence has no effect on projections. No part of the raw file or raw row is sent to an application server.

`reviewImport(case, batch, decisions, command, validateCase)` is a separate operation. It requires one explicit `approve`, `edit`, `reject`, or `exclude` decision per proposal. The entire new case is built in memory and passed to `validateCase`, which must be the production native/WASM case validator before persistence. The operation returns the new immutable case only if all decisions and validation succeed. It adds one artifact and its proposals on first import, and only approved/edited `bank_credit_observed` facts become events. The caller supplies stable event/fact/review IDs, recorded time, and parent heads; there is no hidden clock or random ID source. An exact repeated reviewed command returns the prior case unchanged. Reuse of the same artifact with conflicting decisions fails `IMPORT_CONFLICT`; similar rows from a different artifact are surfaced for review and are never silently deleted. Storage commits the returned case and outbox entry in one local transaction in M6.

`manualFact(case, reviewedInput, validateCase)` accepts explicit typed fields and a manual source marker. It does not claim uploaded-source support. UMD aid-offer, bill, and refund-notice adapters cannot claim compatibility until actual permitted format evidence is recorded. The browser file/worker boundary must copy bytes, preserve cancellation, and never commit a partial import; this remains a separate M5/M6 integration gate.
