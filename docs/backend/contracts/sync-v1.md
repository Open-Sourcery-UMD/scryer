# Ciphertext sync protocol v1

Status: the exact chunk/manifest parser, assembler, and PostgreSQL ciphertext store are implemented and locally tested. A synthetic Chrome outbox was accepted by the independent Python parser and reproduced the same encrypted package digest. The HTTP factory has account, case listing, current and historical ciphertext reads, chunk, manifest, case-delete, initial recovery-wrapper, opaque device-registry, and account-deletion routes tested with a unit-only token verifier and real PostgreSQL. The official browser transport sends saved ciphertext bytes, registers their opaque device IDs, validates receipts, and preserves conflicts; one Chrome/FastAPI/PostgreSQL integration test passes with a clearly synthetic verifier, including browser-generated wrapper storage and fresh-page unlock. The local Keycloak browser PKCE flow is tested separately. The real local Keycloak deletion adapter and restricted runner passed disposable-service tests; a public scheduler is open. A maintained JWT verifier and real token-to-API integration remain blocked. This is a contract, not a claim that a production service is running.

## Identity and transport

The browser uses OIDC authorization code with PKCE and sends an access token in `Authorization: Bearer`. The service validates issuer, audience, algorithm, signature, expiry, not-before, and current account state before any tenant operation. It derives an opaque `accountId` from verified identity and service account state. Every `accountId` in a ciphertext body must match that derived identity. Other body fields never select a tenant. This service does not accept source documents, bank credentials, names, dates, amounts, or decrypted cases.

`/v1` is the only API version. Mutating requests require a bounded `Idempotency-Key`; requests with JSON bodies require `Content-Type: application/json` and the browser's saved exact request bytes. Empty-body DELETE requests reject a body. `/v1` responses use `Cache-Control: no-store`. The current and planned API is:

| Method and path | Request | Success |
| --- | --- | --- |
| `GET /health/live` | none | `200` liveness |
| `GET /health/ready` | none | `200` only when database and auth configuration are ready; otherwise `503` |
| `GET /v1/account` | bearer token | opaque account ID, status, capabilities, quota usage |
| `GET /v1/cases?limit=50&cursor=…` | bearer token; limit 1–200 | opaque case IDs, heads, opaque continuation cursor |
| `GET /v1/cases/{caseId}` | bearer token | current encrypted package and revision metadata, or a generic tenant-scoped `404` |
| `GET /v1/cases/{caseId}/revisions/{revisionId}` | bearer token | authorized retained encrypted package |
| `POST /v1/cases/{caseId}/chunks` | exact `ChunkRequest` and idempotency key | `202` staged chunk receipt |
| `POST /v1/cases/{caseId}/revisions` | exact `ManifestRequest`, idempotency key, and create/update precondition | `201` created or `200` updated; revision and ETag |
| `DELETE /v1/cases/{caseId}` | idempotency key and exact `If-Match` head | `200` opaque tombstone receipt |
| `GET/PUT /v1/account/recovery-envelope` | bearer token; strict encrypted wrapper only | exact encrypted wrapper/version or initial-create receipt; replacement currently returns `409` |
| `GET/POST /v1/account/devices` | bearer token; canonical 16-byte opaque ID for POST | ordered list or registration receipt |
| `DELETE /v1/account/devices/{device_id}` | bearer token; canonical ID, idempotency key, empty body | opaque ID retirement receipt |
| `DELETE /v1/account` | bearer token, exact `X-Confirm-Account-ID`, idempotency key, empty body | `202` deletion reconciliation receipt; ordinary access denied immediately |

No route is considered implemented until its generated OpenAPI contract and integration tests pass. Case listing uses a 15-minute HMAC cursor bound to account ID, exact microsecond `updated_at` and case-ID keyset order. Malformed, expired, and cross-account cursors fail with a typed `400`. A list is not a snapshot across concurrent mutations; clients refresh from the first page after edits. The service does not semantically merge cases. Historical revisions remain authorized and quota-accounted until explicit documented compaction.

Initial recovery setup accepts at most 4096 exact canonical JSON bytes of `RecoveryEnvelopeV1` with `If-None-Match: *` and a saved idempotency key. The server binds its opaque `accountId` to verified identity, stores the exact bytes and SHA-256 digest, and returns generation `1` with ETag `"1"`; `GET` returns those exact bytes. A missing precondition is `428`, a stale one is `412`, changed reuse of a key is `409`, and an oversized body is `413`. The server checks shape and byte integrity, not whether the AES-GCM tag opens with the user's recovery secret. A matching `If-Match` for replacement returns `RECOVERY_ROTATION_UNSUPPORTED` (`409`) because changing the wrapper without atomically changing encrypted case heads and stale-device access could strand data. M8 must establish that account-wide transition before replacement is enabled. The current browser transport does not yet publish wrappers as an ordinary user workflow; the synthetic browser integration test calls the route directly.

The device registry accepts at most 256 canonical JSON bytes with exact keys `schemaVersion`, `deviceId`, where the ID is a canonical unpadded base64url encoding of 16 random bytes. Registration uses the deterministic idempotency key `device:<deviceId>`; retirement uses `device-retire:<deviceId>`. Both serialize under the account row lock. Registration returns an active-ID receipt, and a retired ID cannot be registered again. An account may hold at most 16 active and 256 lifetime IDs; the list includes UTC server timestamps and both limits. A new manifest, including an exact retry after retirement, is refused with `DEVICE_NOT_ACTIVE` unless its ID is active. Chunks can still be staged because the chunk wire has no device ID, but staging never publishes a revision. The browser registers each saved manifest ID before sending ciphertext, retries the exact registration body and key after transport failure, and leaves the outbox intact on refusal.

**ID retirement is not access-token or session revocation.** A valid account token can register a different ID, and retirement does not stop ciphertext reads. The ID supports key-domain separation, bounded metadata, and refusal of writes labeled with a retired ID. Provider session revocation and access-token lifetime controls remain a separate release gate. A browser installation persists its opaque ID after verified recovery unlock; a fresh local database needs a fresh unlocked session and receives a new ID. Recreating an evicted database under the same name also mints a new ID because the old use counter is gone. New-root recovery rotation creates and persists a new ID so its AES-GCM use budget starts under a distinct key domain. An old tab with the old root fails the final account-proof check before a reviewed case write or archive restore.

## Exact prepared chunk and manifest bytes

`client/storage/repository.ts` durably stores the complete chunk and manifest body strings before transmission. They are UTF-8 encoded verbatim on every retry. The server rejects duplicate JSON members, unknown members, reordered members, noncanonical whitespace/escaping/base64url, unsupported versions/algorithms, invalid ID bounds, and any body whose `accountId` differs from the authenticated account. The server's parser compares exact received bytes to canonical JSON reserialization. The on-wire key order is:

```text
ChunkRequest: schemaVersion, kind, accountId, caseId, revisionId, packageId,
              index, chunkCount, nonce, ciphertext, tag
ManifestRequest: schemaVersion, kind, format, algorithm, accountId, caseId,
                 revisionId, deviceId, keyGeneration, packageId, chunkCount,
                 chunkDigests, packageDigest
```

`schemaVersion` is `"1"`; kinds are `"chunk"` and `"manifest"`. The manifest format and algorithm are exactly `"scryer-case-v1"` and `"AES-256-GCM+HKDF-SHA-256"`. Account/case/revision IDs are 1–64 bounded opaque ASCII identifiers per `crypto-v1.md`; 16-byte `packageId` and `deviceId` use canonical unpadded base64url and may begin with `-` or `_`. There are 1–8 chunks, indexed `0..count-1`; nonces are 12 bytes, tags 16 bytes, and nonempty ciphertext chunks at most 4 MiB decoded. `chunkDigests[i]` is lowercase hex SHA-256 of the exact ith chunk body. `packageDigest` is lowercase hex SHA-256 of the browser's ordered serialized `CasePackageV1` constructed from the matching chunks. This digest checks transport assembly; it does not authenticate financial contents or prove that an account holder reviewed them.

The manifest may publish only when every chunk is present, belongs to the same account/case/revision/package, has the declared count/index, matches its exact body digest, and assembles to the declared package digest. Chunks may arrive in any order. A failed manifest leaves the old head intact. A staged chunk is not a visible case revision. The PostgreSQL store enforces 24-hour staging expiry and quota accounting under an account-row lock.

The server accepts at most 8 MiB decoded encrypted envelope bytes (ciphertext plus nonce/tag bytes), 8 MiB per chunk HTTP body, 16 KiB manifest body, and 12 MiB for any HTTP request. The browser's local store can hold a 32 MiB plaintext case, so a case larger than the sync ceiling remains available locally and receives an explicit `413` sync result; a quota failure never erases its local edit.

## Concurrency, retries, and errors

Create uses exactly `If-None-Match: *`. Update and delete use a strong quoted revision such as `If-Match: "rev-demo"`; weak ETags, wildcards for updates, missing headers, and malformed values are rejected. The manifest is the atomic commit boundary. The idempotency identity is the verified account plus key; its digest includes method, path, exact body, and precondition. A replay with the same digest returns the original receipt only while the account/case lifecycle still allows it. Reuse with changed bytes or precondition is `409`. Concurrent manifests on the same head serialize; a stale expected head is `412` and does not overwrite the other branch. A missing required precondition is `428`.

The planned response error shape is `{ "error": { "code": "STABLE_CODE", "requestId": "opaque-id" } }`, without financial data or raw user input. Invalid/expired token is `401`; cross-tenant reads and unauthorized nested resources use indistinguishable `404`; malformed wire is `400`; stale precondition is `412`; idempotency conflict is `409`; size/quota rejection is `413`; rate limiting is `429` with bounded `Retry-After`; database unavailability is `503`. Transport faults alone may be retried with backoff and jitter. The client preserves the prepared outbox and local approved state on every non-successful sync attempt.

`client/sync/transport.ts` accepts only an HTTPS API origin or literal loopback IP HTTP origin, uses a memory-only bearer token, omits cookies, disables redirects, and requests no caching. It checks the authenticated account response before upload, sends saved chunk/manifest body strings and idempotency keys verbatim, validates bounded chunk and manifest receipts against those saved requests, and acknowledges only after a matching strong ETag and digest. A lost manifest response is retried with the same bytes and key, including when the response body stream fails after headers arrive. A stale `412` yields an authorized encrypted head artifact and leaves the local branch pending for reviewed resolution. HTTP `401`, `409`, and `413` stop; network faults and `429`/`503` receive at most three attempts with bounded delay. The browser integration gate currently injects a synthetic token verifier, so it does not establish real provider authentication.

`previewSyncConflict` takes that encrypted `412` artifact and an unlocked local repository. The conflict result binds the pending operation ID, revision, saved manifest SHA-256 digest, and server revision precondition. The preview checks those against the first pending operation, enforces exact canonical remote package JSON and account/case/revision/ETag binding, decrypts and semantically validates the remote case in the browser, then returns the local and remote case/ledger with their event heads. It rechecks the pending identity, local revision, and local ciphertext digest after validation, including when a revision ID has been reused. Bad remote ciphertext or semantic data returns `REMOTE_UNVERIFIED`; changed local state returns `STALE_CONFLICT_PREVIEW`. It never writes or acknowledges the outbox, and no plaintext is sent to the server. The preview does not prove server freshness or authorize a merge; any later reviewed resolution must repeat local and server preconditions.

`analyzeConflictPreview` is a pure, read-only browser analysis of those two validated branches. It returns sorted shared, local-only, and remote-only event IDs; flags same-ID payload collisions, duplicate fact approvals, concurrent corrections, and concurrent match decisions for one refund; and names non-event case fields or the review ledger when they differ. The result contains IDs and issue codes only. An empty issue list is **not** merge permission: no verified common-ancestor package, metadata reconciliation, reviewed resolution, or atomic publish step exists yet.

When a stale upload named an expected server revision, the transport requests `/v1/cases/{caseId}/revisions/{revisionId}` after the current head. A matching, bounded canonical ciphertext package and strong revision ETag become an `available` ancestor candidate; a tenant-scoped `404` becomes `unavailable`; a create conflict with no named base is `not_requested`. The official HTTP transport requires the canonical package member order even though the lower-level in-memory package parser may accept another order. Other HTTP faults keep their normal transport classification, and a malformed `200` fails closed. The browser preview authenticates and semantically validates an available ancestor under the unlocked root, returning it in memory with the two branches. A historical server response alone does not prove that the local branch descended from those exact bytes, nor does it prove server freshness. Reviewed resolution still needs explicit ancestry and decision checks.

`analyzeAncestorCandidate` is a read-only content check over that preview. It reports, separately for local and remote, base event IDs missing or changed under exact canonical payload comparison, non-event case arrays whose base content is not an exact prefix, and a review ledger whose base reviews are not an exact prefix. An event's causal parents are part of the compared payload; event enumeration order is irrelevant. A `baseContentRetained` result means only that these conservative content checks passed. It does not prove that the local revision was derived from those exact historical ciphertext bytes, establish server freshness, settle concurrent decisions, or permit merge/publication. A harmless reorder of non-event arrays can produce a false negative by design. The report contains IDs and field names, never financial values or a merged case.

`proposeDisjointApprovalUnion` is a narrower browser-only, read-only candidate builder over an already decrypted and validated preview. It requires an available historical base candidate whose event and metadata content is retained in both branches, equal current metadata arrays and review ledgers, no identified event/decision collision, and distinct new `approve_fact` events on both branches. It refuses branch-only corrections, match decisions, coverage changes, or overlapping fact/review/proposal/source identities. It returns a canonicalized union case with both branches' heads and a `requiresReview` marker; refusal returns a stable reason code without financial values. The function never writes local state or syncs. The tested positive path is independent manual approvals; concurrent statement imports normally change metadata or review ledgers and are refused. A caller must still obtain explicit human review, validate the candidate with the production engine, prove the intended ancestry and current server precondition, and replace the pending operation atomically before publication. None of those publication steps is implemented by this candidate builder.

`digestDisjointApprovalCandidate` hashes the complete canonical union case and review ledger for the narrow candidate above. `prepareReviewedApprovalJoin` accepts a separate explicit command binding that digest, pending operation/revision/manifest and all saved-step bytes, local ciphertext digest, local/remote/base revisions, each branch's one maximal head, the exact sorted branch-only approval IDs, a new event ID, a new review ID, and a canonical UTC review time. It rebuilds the candidate, checks those bindings, requires exactly the selected two heads, appends a nonmonetary `resolve_branches` event with those parents, and requires a caller-supplied case validator to accept the base, both branches, and joined case. Refusals use stable nonfinancial codes. The result is a new in-memory case with one head, not a durable review record or proof of human inspection. A future UI must show the actual source-backed changes before supplying the command. Current Chrome tests use an injected semantic validator plus native validation outside the browser; production WASM validation is still blocked.

`commitReviewedApprovalJoin` reopens the current encrypted conflict preview using the saved conflict response and reruns the exact review command. `LocalRepository.commitConflictResolution` validates and encrypts the joined case, then in one IndexedDB transaction compares the account root/device, current encrypted case and anchor digest/revision, exactly one byte-identical pending request, and new operation-key availability. It replaces that pending request with a new encrypted joined case and saved outbox operation whose server precondition is the reviewed remote revision. A stale state or transaction abort leaves the old case and request intact. The joined journal retains both immutable parent histories and their branch-specific approved facts; it does not keep a second stale-root ciphertext archive. After reload, the new outbox still has the remote revision as its CAS precondition. Publication uses the server's atomic revision CAS and can return another conflict if the remote head moved; this local transaction alone does not establish current server freshness or a successful published resolution. The narrow path refuses multiple pending edits and divergent statement imports. Real JWT/WASM-backed end-to-end publication and old-client event compatibility remain open.

The local M8-6f synthetic journey now exercises this narrow publication path: two same-account Chrome devices make disjoint manual approvals from one encrypted base; one wins the server CAS, the other receives a conflict, decrypts both branches and the retained historical base, constructs a bound join command, atomically replaces its pending operation, and publishes the joined ciphertext against the winner's revision. The server returns a committed receipt and the browser clears its pending operation. Native validation of the resulting case runs outside Chrome, and a second synthetic tenant receives `404`. The fixture uses a unit-only identity verifier and an injected Chrome semantic validator, and the command is supplied by a test rather than a human review UI. A later server-head advance after local replacement still needs integration coverage; this test does not establish production JWT/WASM operation or public-service readiness.

Server revision, local encrypted-store revision, and domain knowledge head are separate. Successful transport does not approve a financial fact. On two-device divergence, the client must preserve both ciphertext variants and obtain reviewed semantic resolution; no server last-writer-wins path exists.

## Database boundary and migration state

`migrations/0001_sync.sql` creates separate owner, security, and ordinary application roles; opaque ciphertext tables; and forced RLS on all tenant-owned tables. `0002_account_identity.sql` rejects duplicate `(issuer, subject)` mappings. `0003_case_listing.sql` adds the live-case keyset index. `0004_account_deletion.sql` adds irreversible lifecycle columns, a tenant-scoped account deletion function, active-account write guards, a separately restricted worker role, and job lease fields; it refuses legacy lifecycle rows for explicit operator review. The ordinary role cannot read the private context key or deletion jobs, update account lifecycle fields, or delete account rows. `sync/db_context.py` establishes a signed transaction-local account context after the API boundary accepts a verified identity and checks current account state. A raw caller `SET` of account ID is insufficient to cross tenants. See ADR 0005 for the precise guarantee and limits. `sync/migrate.py` records migration SHA-256 checksums in a private table, refuses edits to applied files and unknown future versions, and applies schema changes transactionally. The current 85-test sync suite passed on PostgreSQL 15.11 and 16.15. The HTTP tests use a unit-only identity verifier and do not prove real JWT validation.

## PostgreSQL store behavior

`sync/store.py` requires its caller to open a transaction and set a signed verified tenant context before invoking any store function. The caller must commit that transaction before acknowledging a result to the browser. Under an account-row lock, chunk staging checks lifecycle, tombstones, exact body identity, 24-hour expiry, and the 256 MiB per-account budget. A duplicate chunk with the same bytes is not charged twice. If a staged chunk expires, the browser's exact saved key and body can be retried to restage it; an old receipt alone cannot make a missing chunk appear committed.

Manifest publication obtains the same account lock, checks a strong create/update precondition, validates every exact staged chunk and assembled package digest, then inserts the retained ciphertext revision, changes the case head, removes the used staging bytes, adjusts quota, and writes the idempotency receipt in one transaction. Different requests racing from one head have one winner; the losing staged branch remains until expiry so the client can surface a conflict. The server does no semantic merge. A lost response replay returns the original receipt for an unchanged request, except that deleted or disabled account/case state overrides an old success. The store charges retained package bytes and live staged body bytes; bounded wrapper and metadata bytes are not in this case-ciphertext counter and require separate operational accounting.

`get_head` and `get_revision` verify the stored package SHA-256 before returning ciphertext. Historical retrieval is authorized only for the current tenant while the case remains live; missing and cross-tenant revisions share `404`. Case deletion requires the current ETag, removes retained/staged ciphertext and old case idempotency rows in the same transaction, and keeps an opaque tombstone for the life of the account. Old chunk or manifest retries cannot recreate the case; repeating the exact deletion key returns the tombstone receipt.

Account deletion verifies the opaque account ID returned by `GET /v1/account`, rejects a reused operation key, then changes the account to `deleting`, removes live ciphertext, wrappers, devices, metadata and operation receipts, zeroes the quota counter, and queues provider cleanup in one transaction. Ordinary token use is denied after commit. The worker's lease prevents simultaneous claims; it removes the provider identity before making an anonymous `deleted` tombstone. Confirmed provider failures back off and stop after 20; a failed or missing job makes an exact retry report `503 ACCOUNT_DELETION_STALLED`. A crash before the worker records an outcome leaves the job retryable, and provider `not found` is a successful reconciliation. The real Keycloak adapter and one-shot runner passed a local service-account permission-failure/retry/completion test, but real JWT-to-API denial, a deployed scheduler, backup deletion ledger, and published retention policy remain open. Older backups and offline browsers may still contain ciphertext, so live-row deletion is not physical erasure.
