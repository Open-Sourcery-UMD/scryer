# Scryer encrypted portable archive v1

Status: locally implemented and tested in Chrome with synthetic cases. A production export flow still needs the frontend's save/re-entry UX, browser-native case validation from M4, and independent human security review.

## Bytes and authentication

An archive is one canonical, whitespace-free UTF-8 JSON object with exact fields in this order: `schemaVersion`, `format`, `accountId`, `exportId`, `recoveryEnvelope`, `cases`, `originals`, `authTag`. `schemaVersion` is `"1"`, `format` is `"scryer-encrypted-archive-v1"`, and `exportId` is 16 fresh random bytes in canonical unpadded base64url. Every nested object has the exact field set and order emitted by `client/export/archive.ts`. Ingress fatally decodes UTF-8, parses JSON, reconstructs the defined member order, and compares the reserialization byte-for-byte. Duplicate keys, alternate ordering/spacing, unknown fields, and noncanonical encodings are rejected. The full archive cap is 128 MiB; at most 64 cases and 64 originals are allowed.

`authTag` is a 32-byte HMAC-SHA-256 over the canonical UTF-8 JSON of every archive field before `authTag`. The HMAC key is derived from the account root with HKDF-SHA-256, salt UTF-8 `scryer:archive-auth:v1`, ordered JSON info `{schemaVersion:"1",purpose:"archive-auth-v1",accountId}`, and a 256-bit output imported as a nonextractable HMAC key. This authenticates archive membership as well as ciphertext: removing/reordering a case or original, changing the wrapper, or changing metadata fails before preview. A valid older archive can still be replayed; an existing device reports local revision conflicts, while a fresh device without an independent anchor cannot prove that a valid backup is newest. The archive contains the recovery wrapper but never the plaintext root or secret.

`cases` contains the latest encrypted package, revision, generation, local sequence, and exact package SHA-256 digest for each case. Archive export first validates every case package and its decrypted case/ledger using the configured semantic validator; it then requires re-entry of the recovery secret against the currently stored wrapper. The default `originals` array is empty. An explicit array of caller-provided source bytes may contain at most 16 MiB in total. Each source must match an artifact ID and full SHA-256 in an archived case. Its bytes are base64url-encoded, encrypted as a separate bounded authenticated package, and bound to artifact ID through a purpose-specific derived package case ID and to source SHA-256 through its revision ID. Optional originals are not written to IndexedDB; `extractArchiveOriginals` verifies the archive and returns the bytes to an explicit caller.

Pending outbox entries are not copied into the archive. The latest encrypted case contains the complete approved event history. A restore prepares a fresh ciphertext outbox operation for each replaced case with a null server precondition; M7 must resolve any remote conflict before delivery. Previously pending local operations for a replaced case are deleted in the same local restore transaction.

## Preview and restore

`previewRestore` requires the recovery secret, verifies the wrapper and archive HMAC, authenticates and decrypts every case and optional original, runs the semantic validator on every case/ledger, and reports archived/current revisions and identical-ciphertext status. It writes nothing. `restoreEncrypted` repeats all validation against a stable copy of the input and requires one explicit expected local revision per archived case. A single IndexedDB transaction checks every current revision and digest anchor, then replaces the selected cases, anchors, and prepared outbox operations. A stale revision, wrong secret, bad tag, quota denial, or interrupted transaction leaves every existing case and outbox entry unchanged. The caller must explicitly review any conflict shown in preview.

## Storage migration and recovery

IndexedDB schema v2 adds a schema marker with the SHA-256 of a verified pre-upgrade archive and an outbox `(account,case,localSequence)` index. A populated v1 database refuses ordinary automatic opening with `MIGRATION_REQUIRED`. `migrateLocalDatabase` verifies a canonical encrypted archive against the live v1 wrapper and every exact current case revision/digest, closes the v1 handle, then upgrades in one version-change transaction. The transaction rechecks account wrappers and case identities before writing the v2 marker. A stale backup is rejected. An aborted upgrade leaves v1 and its records intact; the same backup can be used to retry. Post-upgrade readback checks the marker and every case. If post-upgrade readback fails, the encrypted archive remains the portable forward-recovery source in a fresh database. This migration procedure currently supports one account per local database; a database containing multiple accounts fails the backup identity check instead of silently dropping another account.

Browser tests cover default and explicit originals, independent Node/OpenSSL verification of a Chrome-generated archive HMAC, wrong key, duplicate keys, changed case/original/tag, removed case, nonmutating preview, fresh-device restore, stale conflict, second-case write abort, v1 backup freshness, interrupted upgrade, and successful retry. These tests use synthetic validator callbacks because M4 browser C++/WASM validation remains blocked.
