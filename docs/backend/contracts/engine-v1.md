# Engine contract v1

The versioned request is UTF-8 JSON with duplicate object keys rejected at the boundary. Unknown fields fail rather than silently affecting meaning. IDs and canonical semantic output strings are bounded printable ASCII; arbitrary source text remains in local evidence storage and does not enter the canonical receipt. JSON money uses canonical integer strings only. `schemaVersion` is `1`.

`CaseInput` owns `caseId`, explicit `currency: "USD"`, institutions, school terms, local account references, artifacts, proposals, and events. A school term names an institution, one school account reference, and a half-open date interval. A bank account reference has no institution claim. Every `SourceArtifact` has an opaque `artifactId`, locally computed SHA-256, source class, `observedAt` UTC, and an account reference or null. A proposal has provenance but no engine effect. `approve_fact` contains `factId`, term ID or null for a bank observation, account reference or null for certain non-posted roles, explicit `currency: "USD"`, evidence role, nonnegative `amountMinor`, effective source date or null, source reference or a manual marker, and review ID. Posted school movements and issued refunds must bind to the term's school account; bank observations bind to a bank account. A correction contains `factId`, nonnegative replacement amount or a cancellation flag, source reference, and review ID. Every event has `eventId`, `parents`, `recordedAt` UTC, and kind. Events are immutable.

An extraction proposal retains its raw source value, source artifact and position, parser/mapping versions, and nullable normalized proposed cents. An approved fact has nullable `proposalId`. A linked approval must cite the same artifact and source location and each proposal may create at most one approved fact. A null link denotes manual transcription from the cited artifact or a separately marked manual fact. The approved amount may differ from proposed cents after review; the proposal and its original value remain unchanged. Corrections retain their own source/review event. The supported receipt includes proposal ID, proposed cents, and parser/mapping versions for each participating fact, or nulls for manual transcription; raw strings remain in the local case rather than the canonical receipt.

The local reference now has explicit `AidItem(aidItemId, institutionId, termId|null, recipientKind)` records and nullable `Fact.aidItemId`. Linked aid offer, accepted, pending, work-study offer, and school credit facts may form an evidence-only lifecycle. An annual item has a null term and cannot be silently allocated to a term. Offer/accepted/pending records are snapshots, not school-account movements; only linked posted school credits sum into `postedMinor`. Multiple active offer snapshots are ambiguous until reviewed resolution. Parent/third-party recipient metadata produces a verification finding and does not prove a student refund. Surplus receipts include the aid-item ID of each participating fact and the independent checker validates it.

The reference adds `aid_gross_disbursement` and `aid_fee_withheld` roles for an aid item. Both require an `aid_disbursement_statement` artifact, no account reference, and source observation by the review time; corrections have the same source requirement. `LifecycleResult` exposes `gross_disbursed_minor`, nullable `withheld_fee_minor`, and nullable `unexplained_difference_minor` in addition to the existing offer and posted amounts. The difference is computed only with gross and posted evidence. Gross and fee never change school surplus. An offer alone is not gross-disbursement evidence. The fixed corpus includes before/after-fee arithmetic and the unresolved gap.

For M2 the executable operations are:

- `validate_case(case) -> validated case | typed error`.
- `project_school_surplus(case, heads, term_id) -> projection`.
- `compare_school_surplus(case, before_heads, after_heads, term_id) -> comparison`.
- `make_school_surplus_receipt(case, heads, term_id) -> receipt`.
- `check_school_surplus_receipt(case, receipt) -> checker result`, implemented independently from the production engine.

Later required production operations are capability inspection, historical/timeline projection, matching and allocations, coverage, discrepancy queue, source/calculation traversal, batch evaluation, and receipt generation for supported metrics. The Python reference and native core now have coverage, matching, lifecycle, historical-head mapping, school-surplus projection, and receipts; the versioned production CLI and WASM boundary remain open. Other listed operations need detailed schemas and negative tests before implementation. No placeholder success response is allowed.

The local Python reference and native core implement `evaluate_bank_coverage(case, heads, account_ref_id, start_date, end_date_exclusive)`. An `assert_coverage` event records a reviewed `bank_transactions` date interval for one bank account and names its source/basis. A `retract_coverage` event directly names the assertion event as a parent and removes that claim from later snapshots. The evaluator reports exact covered and missing intervals and source-based versus user-based status. Fixed and seeded native parity is locally verified; WASM/browser parity remains open.

The local Python reference also implements `suggest_refund_deposits(case, heads, refund_fact_id, bank_account_ref_id, candidate_limit=1000, window_days=30)`. It searches the selected bank account's approved credits within a bounded heuristic date window, reports the period coverage result, and never treats amount/date agreement as confirmation. A `decide_match` event names the refund fact, bank fact, exact allocated cents, `confirm` or `reject`, and review ID; direct parents include both fact approvals. Later direct-parent decisions supersede earlier decisions for the same pair. Concurrent unresolved decisions are contradictory. Global bank and refund capacity checks reject overallocations, including after fact corrections. An empty candidate list with source-backed period coverage means only `NO_CANDIDATE_IN_APPROVED_FACTS`, with `SOURCE_SET_MAY_BE_INCOMPLETE` and `NOT_PROOF_OF_NONPAYMENT` reason codes.

The reference case contract now requires `holderKind` on account references (`null` for school accounts, a reviewed category for bank accounts), `recipientKind` on facts (a reviewed category for issued refunds, otherwise `null`), and nullable `recipientEvidence` on match decisions. Unknown or mismatched categories suppress automatic suggestions. A cross-recipient confirmation requires an artifact-backed `recipient_instruction` available by the review time; an attached manual marker, wrong artifact kind/account, or future artifact is invalid. These fields are local user-reviewed labels, not external identity authentication. The fixed corpus includes the suppressed-parent-refund and reviewed-instruction outcomes.

The reference and native core `heads_as_known(case, cutoff_utc)` return `EMPTY`, `UNIQUE`, or `AMBIGUOUS` over approved journal events. Neither chooses between divergent heads by event ID or device time. The fixed synthetic parity corpus lives in `tests/reference/corpus/manifest.json`; `docs/backend/release-corpus.md` maps all 48 release scenarios and identifies the many pending browser/server/crypto gates. The native core has fixed and seeded local parity evidence; WASM/browser parity remains open.

Case v1 also recognizes a nonmonetary `resolve_branches` journal event with exactly two distinct existing parent event IDs and the exact payload `{"resolution":{"reviewId":ID}}`. The review ID is globally unique among event review IDs. An incorrect parent count returns `INVALID_RESOLUTION_PARENTS`; repeated IDs, missing parents, repeated review IDs, and extra payload fields retain the existing typed errors. The event's ancestor closure includes both parents, so `current` can name a unique joined head once all earlier heads are included. It neither approves a fact nor chooses between conflicting corrections or match decisions; those still report contradiction until a separate reviewed superseding decision resolves them. A browser workflow to author and publish this event is not implemented. Existing clients that do not recognize this event must be upgraded before joined cases are exchanged; the v1 label alone is not a safe compatibility signal.

The local reference additionally exposes `reproduce_school_surplus_receipt(case, archived)` and `reanalyze_school_surplus_receipt(case, archived, new_heads)`. Reproduction validates the archived receipt independently, then rebuilds it byte-equivalent in its recorded `school-surplus-1` rule and `reference-0.1.0` or `reference-0.2.0` producer label. Reanalysis requires explicit new heads, produces a separate `reference-0.2.0` receipt, and returns the archived digest as linkage metadata. Unknown versions are typed unsupported; neither operation mutates the archived receipt. The two producer labels use the same monetary rule; the version field is local provenance metadata, not proof of which executable produced an externally supplied receipt.

The native engine defaults new and reanalyzed receipts to `native-0.1.0`. Its fixture-only compatibility path can reproduce the two reference labels exactly for differential testing. The digest covers the producer label; it does not authenticate who ran the code. Native historical reproduction rebuilds the receipt from recorded heads and the supplied approved case, and rejects any changed field or digest. The independent Python checker separately verifies the native output against source references and arithmetic. A future rule change needs a new native version and an explicit historical reproduction path.

For a school-surplus query, output includes `schemaVersion`, `engineVersion`, `ruleVersion`, `caseId`, sorted `heads`, `termId`, `status`, `amountMinor` or null, sorted participating `factIds`, and stable limitation codes. A conflicting correction returns `CONTRADICTORY_EVIDENCE` with null amount. If no selected approved facts exist, status is `INSUFFICIENT_COVERAGE` with null amount. A source-based total does not imply the source set is complete.

Canonical semantic serialization uses UTF-8 JSON without whitespace, ASCII keys sorted lexicographically, ASCII string values, arrays in specified order, booleans and null, and no JSON numeric monetary values. Optional absent fields and explicit null are different. Untrusted JSON with duplicate keys is rejected. SHA-256 digests cover the canonical receipt core without the `digest` field or incidental runtime metadata. Native and WASM output must agree byte-for-byte for the canonical semantic subset; randomized ciphertext is compared after decryption, never byte-for-byte.

The first supported receipt has exact top-level fields `schemaVersion`, `engineVersion`, `ruleVersion`, `metric`, `caseId`, `currency`, `heads`, `termId`, `institutionId`, `accountRefId`, `status`, `amountMinor`, `facts`, `limitations`, and `digest`. `heads` and `facts` are sorted by ID. Each fact step has its ID, role, original/current amount, signed contribution, approval/correction event IDs and review IDs, recorded times, effective source date, original source reference, and current source reference. Artifact references include the local artifact SHA-256 and observation time; manual references carry a distinct entry ID. The receipt explicitly says source authenticity is unverified. Its checker validates the stated term, institution, account, currency, and arithmetic against the supplied approved case but cannot certify document authenticity or completeness.

## Native request API and CLI contract

The native core entrypoint is `evaluate(const Request&) -> Response`, where `Request` owns a parsed JSON value and `Response` owns a JSON result. All success responses use exactly `{"schemaVersion":"1","engineVersion":"native-0.1.0","operation":OP,"result":VALUE}`. Request JSON is an exact-key object with `schemaVersion:"1"` and one of the operations below. Every request with case data includes a complete `case` value, except a batch subrequest that shares the batch's validated case. Unknown fields, missing fields, unrecognized operations, or mixed schema versions fail with stable typed errors. Case parsing, money conversion, receipt hashing, and the versioned response wrapper are common to native and future WASM callers. The operation body contains canonical decimal-string money, never JSON numeric money.

| Operation | Additional request fields | Result semantics |
| --- | --- | --- |
| `capabilities` | none | Supported operation names, limits, rule and producer versions. |
| `schema` | none | Case/request schema versions, exact top-level case fields, parser limits. |
| `validate` | `case` | Case ID, sorted event IDs, maximal DAG heads, counts. |
| `project` | `case`, `heads`, `termId` | Full school-surplus projection with explicit heads. |
| `current` | `case`, `termId` | If exactly one maximal journal head exists, its projection; otherwise `EMPTY` or `AMBIGUOUS` with null projection and reason codes. |
| `historical` | `case`, `cutoffUtc`, `termId` | Cutoff mapping and projection only when the mapping is unique. An ambiguous cutoff has no chosen financial amount. |
| `timeline` | `case`, `cutoffsUtc`, `termId` | Ordered array of up to 256 historical results, preserving the caller's cutoff order. |
| `compare` | `case`, `beforeHeads`, `afterHeads`, `termId` | Full exact attribution comparison. |
| `coverage` | `case`, `heads`, `accountRefId`, `startDate`, `endDateExclusive` | Full account-specific half-open coverage result. |
| `matching` | `case`, `heads`, `refundFactId`, `bankAccountRefId`, optional `candidateLimit`, optional `windowDays` | Full conservative candidate and reviewed-allocation result. |
| `lifecycle` | `case`, `heads`, `termId`, `aidItemId` | Full evidence-only aid lifecycle result. |
| `receipt` | `case`, `heads`, `termId`, optional `producerVersion` | Canonical school-surplus receipt; the default producer is `native-0.1.0`. Reference labels are supported for local differential compatibility and are not authentication. |
| `verify-receipt` | `case`, `archived` | `{"valid":true,"code":"VALID"}` only when historical reproduction against the supplied approved case succeeds; failure is a typed nonzero error. |
| `reproduce-receipt` | `case`, `archived` | Byte-equivalent archived receipt rebuilt under its recorded heads and supported producer. |
| `reanalyze-receipt` | `case`, `archived`, `newHeads`, optional `producerVersion` | New `native-0.1.0` receipt plus `priorDigest`; never overwrites the archive. The optional reference label is only for differential compatibility. |
| `discrepancy-queue` | `case`, `heads`, `termId`, `aidItemIds`, `matchTargets` | Deterministic review items for one explicit school projection, selected aid items, and selected refund/account pairs. Both lists are bounded to 100; targets are exact objects with `refundFactId` and `bankAccountRefId`. Each item has `category`, `status`, sorted `evidenceFactIds`, sorted `findingCodes`, sorted `nextActionCodes`, and `priority:"review"`. This priority is workflow order, not financial urgency. No item asserts a legal deadline, entitlement, or nonpayment. The queue and its items are sorted by category and target IDs. |
| `trace` | `case`, `heads`, `factId` | Approval and selected correction event IDs, original/current exact cents, original/current source references with artifact digest and observation time, and a school-surplus contribution only for a posted term/account school fact. Unknown or conflicting facts fail typed. |
| `batch` | `case`, `requests` | Up to 100 exact subrequests from the listed case-bound operations, excluding `batch`, `demo`, `capabilities`, and `schema`. They share one validated case. The result is an array of exact `{"operation":OP,"result":VALUE}` objects. Any failure aborts the entire batch; no partial successful array is returned. |
| `demo` | none | Built-in synthetic golden case before/after projection, exact `-60000` attribution, receipt, and separate refund/bank observations; no account, network, external file, or real records. |

All explicit `heads` arrays contain unique existing event IDs; empty heads select no approved events. `current` never chooses one of multiple maximal DAG heads by timestamp or lexicographic ID. `historical` and `timeline` keep the cutoff mapping's `EMPTY`, `UNIQUE`, or `AMBIGUOUS` status and reason codes. Calculation and source traversal use the same approved snapshot rules as projection and receipts. Queue generation cannot upgrade a suggestion to a reviewed match. The test-only reference producer option does not certify which executable generated a receipt.

The CLI executable is `scryer-native`. `scryer-native --help` prints usage and exits 0; `--version` prints `native-0.1.0` and exits 0; `scryer-native demo` runs the embedded synthetic case. Otherwise it reads one request from stdin or `--input PATH` and writes one canonical success response to stdout or `--output PATH`. It reads at most 20 MiB plus one sentinel byte before the JSON parser, enforces depth 64 and 200000 events through the common boundary, and never performs network I/O. A requested output file is written to a temporary file in the same directory and atomically renamed only after evaluation succeeds. Exit codes: `0` success; `2` invalid CLI usage; `3` invalid JSON, schema, or semantic input; `4` receipt verification failure; `5` file I/O failure; `6` computation or resource limit. On validation or evaluation failure stdout is empty and a specified output path is not replaced; stderr contains only canonical `{"schemaVersion":"1","error":{"code":CODE}}` without financial values. A failing stdout transport can expose a partial write despite the nonzero I/O exit code, so callers needing atomic files use `--output`. The CLI is a file/stdio boundary and does not add clocks, randomness, filesystem discovery, or persistence to the pure core.
