# M8-5c read-only base-content compatibility

**Goal:** Compare an authenticated historical revision candidate with the local and remote browser-validated branches. Report whether each branch still contains the candidate's exact approved events, case metadata prefix, and import review prefix. This is content compatibility, not proof of local derivation, server freshness, or permission to merge.

**Task ID and risk:** M8-5c, HIGH. **Requirements:** S-60, S-69. **Depends on:** M8-5a read-only branch analysis and M8-5b historical candidate inspection. **Files:** `client/sync/analysis.ts`, `tests/client/test_conflict_analysis.mjs`, `tests/browser/test_conflict_preview.mjs`, the sync contract, and backend status/verification/traceability ledgers.

**Interface:** Export `analyzeAncestorCandidate(preview: ConflictPreview): AncestorCandidateAnalysis`. `not_requested` and `unavailable` remain distinct. For `available`, return the candidate revision and a report for each branch: sorted `missingBaseEventIds`, sorted `changedBaseEventIds`, sorted `changedCaseFields`, `changedLedgerPrefix`, and `baseContentRetained`. Never return financial values, raw source text, or a proposed merged case.

**Comparison rule:** First validate the candidate revision equals the pending expected server revision, the case identity and ledger shape, and unique bounded event IDs. Compare base events by ID and canonicalized full event payload, including causal parents. For each non-event case array and the review ledger, require the base sequence to be an exact canonical prefix of the branch sequence. This conservative rule may report incompatibility for a harmless reorder; it must never call such a reorder a verified extension. The report is pure and does not write, acknowledge, or publish anything. It does not infer byte-level ancestry from matching content.

**Alternatives reviewed:** A revision-ID match alone is insufficient because identifiers can be reused or server history can be rolled back. A union of both branches without base comparison could duplicate decisions and erase prior evidence. A permissive multiset comparison of metadata could mistake a meaningful reorder for an extension. Prefix comparison is intentionally conservative until reviewed resolution rules are defined.

**Tests:** Add a headless red-green test in which both branches add distinct events after an identical base and append complete synthetic metadata/reviews; the report must mark both as content-retaining, be order-independent for event enumeration, and expose only IDs/codes. Add a red-green mismatch test for a changed same-ID base event, a missing base event, a changed metadata prefix, and a changed ledger prefix. Add unavailable/no-base and wrong candidate revision refusal. Validate the headless candidate and both branches with the native C++ case parser. Extend the existing real Chrome conflict preview test to call the analyzer on a nonempty decrypted three-branch preview and independently validate those cases with the native CLI. Run full client typecheck, headless tests, browser build, and Chrome tests. Because this slice changes no HTTP or database code, the existing synthetic Chrome/API/PostgreSQL integration from M8-5b remains the transport evidence.

**Done when:** The report is deterministic, read-only, and value-free; true means only exact candidate content retention under these rules. Focused automated review has no unresolved Critical or Important defect, and all named local gates pass.
