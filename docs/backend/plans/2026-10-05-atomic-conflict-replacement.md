# M8-6e atomic local conflict replacement

**Task ID, requirements, and risk:** M8-6e; S-60, S-69; CRITICAL. Depends on M8-6c causal join event, M8-6d bound in-memory review command, and M6-3 encrypted IndexedDB/outbox transactions. Files: `client/storage/repository.ts`, `client/sync/conflict.ts`, a narrow orchestration module under `client/sync/`, Chrome storage/conflict tests, sync contract, and evidence ledgers.

**Design review:** A normal `commitReviewed` appends an outbox operation and cannot safely replace a stale conflicting operation. The reviewed causal join contains all existing events from both branches, with their original parent IDs, and their current metadata and review ledgers are equal under the narrow candidate rule. Thus the joined case itself retains both financial histories. Keeping a second ciphertext archive would introduce stale-root data that existing key rotation and export do not migrate, so this slice does not create one.

**Interface:** Extend `ConflictPreview` with the locally verified ciphertext digest and a digest of all saved pending request steps. `commitReviewedApprovalJoin` reopens the encrypted conflict and reruns the exact review command before calling a narrow repository replacement method. The repository validates and encrypts before opening a transaction. The transaction rechecks the account root/device, case/anchor revision and digest, exactly one pending request with byte-identical steps, and operation-key uniqueness. It then deletes only that pending request and inserts the joined encrypted case/anchor/outbox with `expectedServerRevision` equal to the reviewed remote revision. Any mismatch, quota fault, or abort leaves all prior records intact. The server CAS is the publication freshness check; a later remote race returns another conflict without losing the local join.

**Invariants and limits:** Do not expose plaintext to the API. Do not drop a chain of multiple pending operations; refuse this narrow path. Acknowledging or retrying the old pending operation after replacement fails typed. Both parent heads and every approved event remain inspectable inside the joined case after reload. The old ciphertext request is replaced atomically; no second local archive is retained. No HTTP call occurs inside the IndexedDB transaction. Full backup/recovery and retention policy remain separate release gates. Production WASM validation and real JWT-to-API validation remain blocked externally.

**Tests/done:** Red-green Chrome regressions on an actual encrypted case and pending outbox: successful one-pending replacement retains both approved branches in the joined journal; stale local revision, changed local digest, changed pending bytes, second pending operation, duplicate new operation ID, simulated quota/transaction abort, and stale account root leave original case/outbox untouched. Reload the page and confirm the joined history and new saved request with its exact server precondition. Run typecheck, browser build, focused Chrome and full relevant headless tests. Do not mark conflict resolution complete until the server CAS journey is exercised with this replacement and old-parser compatibility is addressed.
