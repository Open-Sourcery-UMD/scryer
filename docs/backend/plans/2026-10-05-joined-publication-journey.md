# M8-6f synthetic joined-case publication journey

**Task ID, requirements, and risk:** M8-6f; S-57, S-59, S-60, S-69, RC-31, RC-34, RC-35; HIGH. Depends on M8-6e atomic local conflict replacement, M7 ciphertext CAS API, and the existing synthetic Chrome/FastAPI/PostgreSQL journey. This is integration evidence for the narrow disjoint manual-approval resolution path, not a public deployment claim.

**Design:** In a disposable local PostgreSQL database, use actual Chrome IndexedDB/WebCrypto and browser fetch to the loopback FastAPI fixture. Upload one encrypted base case, make two devices approve distinct synthetic bank observations from that base, let one publish and the other receive a typed CAS conflict. Browser-decrypt the retained base and both branches, bind a complete review command, atomically replace the losing device's pending request with a `resolve_branches` case, then publish the saved joined ciphertext against the winner's revision. Check that the server head is the joined revision, the local outbox is empty only after a validated receipt, and the joined case includes both original branch events. Check the unreviewed source-text sentinel in the decrypted case and its absence from browser API request bodies, HTTP ciphertext, collected loopback logs, and disposable database columns. Validate the joined case through the native CLI outside Chrome.

**Limits and next gate:** The API fixture injects a synthetic unit verifier and Chrome injects semantic case validation rather than the production WASM engine. M8-6g extends this journey with a remote head advancing again after a reviewed local replacement and checks that the joined branch remains pending through another CAS conflict. Real JWT/WASM integration, user-facing review UI, old-client compatibility, and public operations remain open.

**Done:** The local journey passes from a clean synthetic database, with no plaintext marker on the tested transport/storage surfaces and no data loss across one reviewed merge. Exact verification commands and counts are recorded. The status remains `BACKEND_PARTIAL_LOCAL`.
