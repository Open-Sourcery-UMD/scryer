# M6 local encryption and storage design v1

Status: selected for local implementation on 2026-10-04. Independent human security review, cross-browser results, and production deployment remain open. This document refines `crypto-design.md`; it does not certify the implementation.

## Purpose and boundary

The browser keeps the approved `CaseV1` and `ImportLedger` in one encrypted `StoredCaseV1` JSON payload with exact fields `{schemaVersion:"1",case,ledger}`. The case ID inside the decrypted payload must equal the authenticated envelope case ID. A review command returns a complete new pair only after case validation; the repository persists that pair and its prepared sync outbox record in one IndexedDB transaction before acknowledging success. The worker never receives a key or approved history. Raw input files are not persisted or synced by default. A source hash/position remains in the case; a second device reports the original unavailable until the user reattaches matching bytes.

The sync server will see account/case IDs, revision/package IDs, ciphertext sizes, and timing. It must never receive plaintext facts, source bytes, or a recovery secret. The browser, delivered JavaScript, and an unlocked device are trusted for plaintext handling. This design cannot promise protection against their compromise or server rollback on a new device without an independent anchor.

## Key hierarchy and recovery

- Generate a 32-byte account root and a separate 32-byte recovery secret with `crypto.getRandomValues`. Encode the recovery secret as canonical unpadded base64url with a visible `scryer-recovery-v1:` prefix. It is not derived from email, login password, or a PIN.
- Import the root as a nonextractable HKDF key. Derive a 256-bit AES-GCM case key using HKDF-SHA-256 with the fixed UTF-8 salt `scryer:case-key:v1` and the exact ordered UTF-8 JSON info `{schemaVersion,purpose,accountId,caseId,keyGeneration,deviceId}` with `purpose:"case-payload-v1"`. Including the device ID makes simultaneous offline devices use different AES keys even at the same generation. A receiving device derives the sender's case key from the authenticated envelope header and the shared root.
- A fresh 16-byte salt and exact ordered UTF-8 JSON info `{schemaVersion,purpose,accountId}` with `purpose:"recovery-wrap-v1"` derive a distinct AES-256-GCM wrapping key from the high-entropy recovery secret. Wrap the 32 raw root bytes with a fresh 12-byte random nonce. The recovery envelope authenticates version, algorithm, account ID, salt, and nonce as associated data. No plaintext root or recovery secret enters IndexedDB or the sync API.
- Recovery setup is not complete until the user re-enters the secret and `verifyRecoverySecret` successfully unwraps the root and matches a purpose-separated HKDF verification derivation (`scryer:recovery-verify:v1` salt, ordered account-bound info) from the live session. A second device receives the secret from the user and uses the wrapper to unlock. Losing every unlocked device and the recovery secret is unrecoverable by the service.
- Lock drops the session's reference to the imported root. Callers must discard their own decrypted case objects; JavaScript garbage collection prevents a promise of immediate physical memory erasure. A login password reset does not replace or reveal the root.

## Envelope and byte limits

`CasePackageV1` has exact fields `schemaVersion`, `format`, `algorithm`, `accountId`, `caseId`, `revisionId`, `deviceId`, `keyGeneration`, `packageId`, and `chunks`. IDs use the case contract's bounded ASCII pattern. `packageId` and `deviceId` are each 16 random bytes encoded canonical base64url. A package contains 1–8 chunks for at most 32 MiB of UTF-8 JSON plaintext. Each chunk holds exact fields `index`, `nonce`, `ciphertext`, and `tag`; plaintext chunks are at most 4 MiB. The nonce is 12 random bytes and tag is 16 bytes. Ciphertext and tag use strict unpadded base64url. An 8 MiB server request limit will require chunk transport plus an atomic manifest commit in M7; a full package is never assumed to fit one request. The 100,000-row CSV cap is a parser safety cap, while a 32 MiB approved payload cap is a separate typed `CASE_TOO_LARGE` limit.

For each chunk, AES-GCM associated data is UTF-8 JSON with exact field order: `schemaVersion`, `format`, `algorithm`, `accountId`, `caseId`, `revisionId`, `deviceId`, `keyGeneration`, `packageId`, `chunkIndex`, `chunkCount`, `nonce`. All strings are ASCII with bounded lengths and exact validation before use. The package fields, chunk count, index, and nonce are therefore authenticated. The package ID is newly random for every encryption operation; a revision ID is never used to justify a nonce reuse. Missing, duplicated, reordered, or mixed chunks fail before plaintext is returned. Decryption buffers all verified chunks and returns no partial plaintext on failure. UTF-8 decoding is fatal, and the repository validates the decrypted case and ledger before presenting them.

`RecoveryEnvelopeV1` has exact fields `schemaVersion`, `format`, `algorithm`, `accountId`, `salt`, `nonce`, `ciphertext`, and `tag`. Its associated data is the exact ordered JSON of all header fields through `nonce`. Unknown versions/algorithms, noncanonical base64url, wrong binding, wrong generation, truncation, bad tag, and over-limit lengths are rejected typed. No dynamic algorithm selection is taken from an envelope.

Every case key is limited to at most `2^20` AES-GCM encryptions. Each `(account,case,generation,device)` reservation counter is stored durably before encryption, and failed operations consume reservations. A fresh random 96-bit nonce still has a collision probability; at `2^20` uses the birthday bound is approximately `2^-57`. Random device IDs can also collide with negligible probability, not impossibility. Loss or ambiguity of a device counter forces a new device ID or generation before another encryption. No deliberate key/nonce reuse is allowed.

## Local repository and sync handoff

IndexedDB v2 stores only the authenticated recovery wrapper, a purpose-separated root proof, nonsecret device/generation metadata and budget reservations, encrypted case packages, encrypted outbox requests, locally remembered revision/digest anchors, and a schema migration marker. Its case key is `(accountId,caseId)`; the repository never stores plaintext cases, ledgers, original files, recovery secrets, or session keys. A single `readwrite` transaction checks the expected local revision and writes the next case package, anchor, and prepared outbox entry. Success is returned only from `transaction.oncomplete`; `onabort` and `onerror` return typed failures. A concurrent stale revision fails instead of replacing approved history. The durable per-device use reservation is a separate earlier transaction, so failed encryption or stale commit consumes the reserved uses.

The outbox stores a prepared sequence of exact serialized ciphertext requests: one per encrypted chunk, then an authenticated manifest commit, each with a stable idempotency ID derived from the local operation ID and step index plus the intended transport precondition. Each chunk request stays below the 8 MiB server envelope limit after encoding. Network failure does not reverse a committed local edit. Retry sends each persisted byte string and ID unchanged. A local edit may create a new package/revision; it does not mutate an existing prepared request. The server's transport revision and the domain knowledge heads are separate from the local revision. M7 must provide chunk staging and atomic manifest commit; it must not silently truncate a case.

The repository distinguishes storage denied, unavailable, quota exceeded, corrupt record, stale local revision, and locked session. On startup, incomplete IndexedDB transactions are absent, while committed outbox entries survive reload. Browser storage can still be evicted by the platform; the app must not claim durability beyond the browser's guarantee. Export is the portable safety path.

## Export, restore, migration, and rotation

An encrypted portable archive contains exact versioned metadata, the recovery envelope, the latest case packages, and optional separately encrypted original files only by explicit choice. A root-derived HMAC authenticates the complete archive membership and metadata, so whole-case removal is detected as well as chunk tamper. Preview restore authenticates and decrypts every package with the supplied recovery secret, validates all cases/ledgers, checks size/schema versions, and shows conflicts without changing the current store. Restore is a separate atomic replace/merge command with an expected local revision for each archived case. A wrong key or tampered archive cannot partially import content. An old backup continues to require the secret valid when it was created. The latest case includes approved history; restore prepares new ciphertext outbox operations instead of replaying old pending transport requests.

Schema migration from populated v1 to v2 requires a verified encrypted archive matching every current case and account wrapper. The version-change transaction checks these identities again; an interrupted upgrade rolls back to v1, while a retained archive supports forward recovery in a fresh database if post-upgrade readback fails. Data-key rotation advances `keyGeneration`, reserves new keys, re-encrypts all retained packages, verifies decryption, then atomically marks the new generation active. The root remains the recovery anchor; this rotation addresses case-key nonce budget, not root compromise. Recovery-secret rotation instead rewraps the same root with a new independently generated secret and only retires the old wrapper after verification and an explicit recovery transition. Sync handling of old packages and two-device races remains an M8 gate.

## Verification gates

Test AES-GCM and HKDF browser output against independent Node `crypto` implementations using fixed synthetic inputs, not only same-code round trips. Test strict format validation, wrong key/account/case/revision/device, every authenticated header field, nonce/tag/ciphertext tampering, chunk loss/mixing, unsupported version, counter exhaustion, and randomized repeated encryption. Run real-browser IndexedDB tests for transaction abort, reload/outbox persistence, concurrent CAS, quota/denial simulation, lock/unlock, second-device recovery, export preview/restore, migration interruption, and rotation interruption. Keep M6 `IN_PROGRESS` until these actual gates pass; no independent audit is implied.

## Alternatives considered

A login-password-derived data key would make password reset and weak-password attacks dangerous, so recovery uses a separate random secret. A server-held recovery master would let the service decrypt user cases and violate the product's privacy boundary. One encrypted blob per complete case would be simpler but conflicts with the 8 MiB server request limit for larger reviewed histories; bounded authenticated chunks are selected despite the additional manifest and atomic-commit work. Deterministic nonces were rejected because offline devices and interrupted writes make a shared counter difficult to coordinate safely; per-device keys plus random nonces and durable per-key use budgets are selected.
