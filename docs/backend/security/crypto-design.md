# Cryptographic design gate — proposed v1

Status: locally selected design, refined by `local-storage-design.md` for M6 implementation. No independent human security review or deployed-security claim has been made.

Use browser WebCrypto AES-256-GCM for case payloads and key wrapping, HKDF-SHA-256 for purpose-separated 256-bit keys, and the browser cryptographic random source for all 256-bit secrets and 96-bit nonces. Do not use an ordinary login password or PIN as a data key. Generate a random account root key locally. Derive a per-case/per-generation/per-device key with an HKDF context containing opaque account ID, case ID, generation, random device ID, and purpose. Generate a separate 256-bit recovery secret locally; derive a wrapping key with a distinct context and random salt to wrap the account root. The server may store only that authenticated wrapped root and bounded metadata. A second device must receive the recovery secret from the user and successfully unwrap before any case decryption. Exact format and byte bounds are in `local-storage-design.md`.

Each encrypted envelope includes version, algorithm ID, key generation, opaque account/case identifiers, logical client revision ID, random nonce, ciphertext, and authentication tag. Canonical encoded header fields are authenticated as AES-GCM additional data. Reject unknown versions/algorithms, unsupported key generations, mismatched binding, bad tag, truncation, and malformed base64url before returning plaintext. A prepared encrypted outbox request is persisted atomically with its local change and retried byte-for-byte under the same idempotency key; a server transport revision is a precondition, not a reason to reuse a nonce with different plaintext.

Random 96-bit nonces have a collision probability, not a guarantee of uniqueness. Limit each derived case/device/generation key to at most `2^20` encryption operations and rotate before the limit; the birthday bound at that cap is approximately `2^-57`. Distinct random device IDs select distinct derived keys, so offline devices do not share a nonce budget for one key. Reserve operation counts durably before encryption; if the counter is lost or ambiguous, use a new device ID or generation. Never deliberately reuse a key/nonce pair. Before implementation, verify the selected browser APIs and an independent AES-GCM/HKDF known-answer or interoperability vector against pinned versions.

No plaintext key persists in IndexedDB. The locally stored wrapped root requires the recovery secret on each fresh unlock unless a separately reviewed device-unlock mechanism is added. Lock drops application references to keys and plaintext; JavaScript garbage collection does not guarantee memory erasure. Recovery setup requires a re-entry test of the secret. Losing the secret and all unlocked devices is unrecoverable by the service.

Rotation is a journaled operation: create a new generation, re-encrypt all retained case revisions and wrappers, verify decryptability, then mark the new generation active. Interruption retains enough old material locally to resume or roll back without losing approved history. Old encrypted backups retain their old key requirement; they are not silently upgraded. An implementation must test interruption, wrong-key and tamper paths, cross-browser round trips, and a second-device recovery flow before this gate is closed.

This design does not defend against malicious delivered JavaScript, a compromised unlocked device, server denial of service, or a new-device server rollback without an independent trusted anchor. The existing `encryption.py` helper is not this protocol.
